## Overview
This file defines a structured hierarchy of custom exceptions used across the Dari backend. By inheriting from a base `DariException`, the system can implement unified error handling and filtering, distinguishing between infrastructure failures, logic errors, and external API timeouts.

## Architecture Role
- **Layer**: Core / Cross-cutting Concern.
- **Pattern**: Exception Hierarchy.
- **Dependency direction**: This is a leaf-level module; it is imported by almost every other module in the backend (Services, Agents, and API layers) to signal specific failure states.

## Key Concepts (Basics → Advanced)
1. **Base Exception**: `DariException` serves as the root. This allows the global error handler (e.g., in a FastAPI middleware) to catch any "known" system error while letting unexpected Python crashes (like `KeyError`) bubble up separately.
2. **Domain Categorization**: Exceptions are grouped by the functional area they impact:
    - **Agentic**: `AgentError` handles failures in agent execution.
    - **Spatial/Navigation**: `RouteError` and its child `GeocodeError` handle GIS and mapping failures.
    - **External AI**: `LLMError` handles failures in the language model interface.
    - **Knowledge Base**: `DocumentError` handles RAG or file-system failures.
3. **Specialization**: The relationship between `GeocodeError` and `RouteError` demonstrates a "is-a" relationship, where a geocoding failure is specifically a type of routing failure.

## Data Flow
Since this file contains only class definitions, there is no operational data flow. However, the logical flow of these exceptions is as follows:
1. **Trigger**: A failure occurs in a service (e.g., `LLMService` fails to connect).
2. **Raise**: The service raises the specific exception (e.g., `raise LLMError("API Timeout")`).
3. **Propagation**: The exception bubbles up the call stack.
4. **Catch**: A high-level controller or middleware catches `DariException` to return a standardized JSON error response to the client.
