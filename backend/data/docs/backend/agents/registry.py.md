# backend\agents\registry.py — Centralized agent lookup and management system

## Overview
This file implements a singleton registry that acts as a central directory for all AI agents within the Dari system. It allows different components of the application to register agent instances and retrieve them by a unique string identifier without needing direct imports of the agent classes.

## Architecture Role
- **Layer**: Infrastructure / Service Locator.
- **Pattern**: Singleton / Registry Pattern.
- **Dependency direction**: Receives calls from agent initialization scripts and service layers; provides agent instances to the orchestrator and other agents.

## Key Concepts (Basics → Advanced)
1. **Case-Insensitive Mapping**: The registry uses `.lower()` on all keys during registration and retrieval, ensuring that `PlannerAgent` and `planneragent` are treated as the same entity to prevent runtime crashes due to casing mismatches.
2. **Decoupling**: By using the `registry` singleton, the system achieves loose coupling. A module can request the "navigator" agent without knowing exactly which class implements that logic or where it is instantiated.
3. **Dynamic Registration**: Agents can be added to the system at runtime via the `register` method, allowing for modular plugin-like architectures where new agents can be injected into the system without modifying the core registry code.

## Data Flow
1. **Registration Phase**: An agent instance is created $\rightarrow$ `registry.register("name", instance)` is called $\rightarrow$ The instance is stored in the `_agents` dictionary.
2. **Retrieval Phase**: A service calls `registry.get("name")` $\rightarrow$ The registry normalizes the string to lowercase $\rightarrow$ The corresponding agent instance is returned from the dictionary.
3. **Validation Phase**: A service calls `registry.has("name")` $\rightarrow$ The registry checks for the key's existence $\rightarrow$ A boolean is returned.

## Gotchas & Extension Points
- **Type Safety**: The registry uses `Any` for agent types. If the system grows, this could be replaced with a BaseAgent abstract class to ensure all registered objects adhere to a specific interface.
- **Overwrite Risk**: Currently, calling `register` with an existing name will silently overwrite the previous agent. Adding a check to prevent accidental overwrites may be necessary for stability.
- **Extension Point**: This file could be extended to support "Lazy Loading," where the registry stores a factory function or class instead of an instantiated object, creating the agent only upon the first `get()` call.
