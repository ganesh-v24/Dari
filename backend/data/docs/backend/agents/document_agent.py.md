# backend\agents\document_agent.py — Agentic documentation generation engine

## Overview
`DocumentAgent` is a specialized agent designed to automate the creation and maintenance of technical documentation for the Dari project. It crawls the source tree, analyzes code using a local Ollama LLM, and generates structured Markdown files that describe the purpose, architecture, and API of every single-source file.

## Architecture Role
- **Layer**: Agent Layer.
- **Pattern**: Strategy / Pipeline (Scan $\rightarrow$ Analyze $\rightarrow$ Write).
- **Dependency Direction**: 
    - Receives calls from the `registry` (via the main agent orchestrator).
    - Calls the local Ollama API via `httpx`.
    - Interacts directly with the local filesystem (`Pathlib`).

## Key Concepts (Basics $\rightarrow$ Advanced)

1. **File Crawling & Filtering**: The agent uses `os.walk` to find files. It employs `SKIP_DIRS` and `SKIP_FILES` to avoid documenting noise (like `.git` or `node_modules`) and `DOCUMENTABLE_EXTENSIONS` to ensure only relevant source code (Python, JS, TS, etc.) is processed.
2. **Change Detection (Hashing)**: To avoid redundant LLM calls, the agent maintains a `.file_hashes.json` file. It calculates an MD5 checksum of each file; if the hash hasn't changed since the last run, the file is skipped during "update" mode.
3. **Prompt Engineering**: The agent uses two distinct system prompts:
    - `SYSTEM_PROMPT`: Enforces a strict, verbatim Markdown structure for individual file documentation.
    - `ARCH_SYSTEM_PROMPT`: Instructs the LLM to synthesize a high-level system overview based on summaries of all files.
4. **Documentation Hierarchy**:
    - **File Docs**: Detailed analysis of a single file.
    - **ARCHITECTURE.md**: A global view of the project vision and request lifecycle.
    - **INDEX.md**: A generated table of contents linking all documentation files.

## Data Flow

1. **Trigger**: User sends a query (e.g., "document all").
2. **Discovery**: `_all_project_files()` identifies all valid source files in the project root.
3. **Filtering**: `_file_hash()` compares current file checksums against `.file_hashes.json`.
4. **Analysis**: 
    - Source code is read via `_read_source()`.
    - Code + `SYSTEM_PROMPT` is sent to Ollama via `_call_llm()`.
5. **Persistence**: 
    - The resulting Markdown is written to `backend/data/docs/` using `_write_doc()`.
    - Updated hashes are saved back to `.file_hashes.json`.
6. **Synthesis**: A JSON summary of all files is sent to the LLM to generate `ARCHITECTURE.md`.
7. **Indexing**: `_build_index()` creates a master list of all generated docs.

## Dependencies
- `httpx`: Used for asynchronous HTTP requests to the Ollama API.
- `pathlib`: Used for robust cross-platform filesystem path manipulation.
- `hashlib`: Used to generate MD5 checksums for change detection.
- `loguru`: Used for structured logging of the documentation process.
- `agents.base.BaseAgent`: The base class providing the agent interface.
- `agents.registry`: Used to register the agent so it can be invoked by the system.

## Gotchas & Extension Points
- **LLM Context Limits**: For the `ARCHITECTURE.md` generation, the agent truncates file summaries to 300 characters (`v[:300]`) to avoid overflowing the LLM's context window. If the project grows significantly, a more sophisticated RAG or recursive summarization approach may be needed.
- **Local LLM Dependency**: The agent assumes Ollama is running on `localhost:11434`. This can be extended by moving `OLLAMA_URL` and `MODEL_NAME` to a configuration file.
- **Timeout Handling**: Large files may cause the LLM to take longer than the default 120s timeout; `_generate_architecture_doc` specifically increases this to 180s.
- **Extension Point**: One could add a "Review Mode" where the agent proposes documentation changes as a diff rather than overwriting files directly.
