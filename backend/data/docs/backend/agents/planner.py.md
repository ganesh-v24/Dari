# backend\agents\planner.py — Orchestration and task decomposition for AI navigation

## Overview
The `planner.py` file implements the `PlannerAgent`, which serves as the central dispatcher for the Dari system. It analyzes incoming user requests using keyword-based pattern matching to decompose complex queries into a sequence of discrete tasks assigned to specialized agents. This file ensures that user intent is mapped to the correct functional module (e.g., routing, memory, or documentation) without requiring a heavy LLM call for the planning phase.

## Key Concepts (Basics → Advanced)

### 1. Task Decomposition
The system uses a `Task` data class to encapsulate a unit of work. Each task defines which agent should handle the request, the specific instruction to follow, and any dependencies on previous tasks.

### 2. Keyword-Driven Intent Recognition
Instead of using a probabilistic LLM for planning, the `PlannerAgent` uses deterministic regular expressions (`_ROUTE_PATTERNS`, `_LOCALITY_PLACE_RE`) and keyword sets (e.g., `_MEMORY_KEYWORDS`). This ensures low latency and predictable routing for common navigation commands.

### 3. Instruction Formatting
The planner transforms raw user text into structured "command strings" for specific agents. For example, a routing request is converted into a pipe-delimited format: `ROUTE|start|end` or `FIND|location`.

### 4. Sequential Execution and Side Effects
The `execute` method processes the planned tasks sequentially. It includes a specific side-effect mechanism where successful `route` agent results are automatically passed to the `memory` agent via `record_route` to maintain a history of user trips.

## Data Flow

1. **Input**: `user_message` (string) is passed to `execute()`.
2. **Planning**: `plan()` scans the message against regex patterns and keyword lists.
3. **Task Generation**: A list of `Task` objects is created (e.g., `Task(agent_name="route", instruction="...")`).
4. **Dispatch**: For each task, the `registry` is queried to retrieve the corresponding agent instance.
5. **Execution**: The specialist agent's `execute()` method is called with the formatted instruction.
6. **Post-Processing**: If a route was successfully found, the `memory` agent is called to store the coordinates.
7. **Aggregation**: 
    - If one task was executed, its result is returned directly.
    - If multiple tasks were executed, their contents are merged into a single "chat" type response.
8. **Output**: A `Dict[str, Any]` containing the final response or aggregated content.

## Gotchas & Extension Points

### Gotchas
- **Keyword Overlap**: If a user message contains keywords from multiple categories (e.g., "Find the history of Paris"), the planner will generate multiple tasks. The order of checks in `plan()` determines the order of execution.
- **Registry Dependency**: If a specialist agent is not registered in the `registry` object, the planner catches the `KeyError` and returns a chat error message rather than crashing.

### Extension Points
- **LLM Integration**: The `plan()` method could be extended to use an LLM for "Complex Planning" if no keywords are matched, replacing the current fallback to the `dari` chat agent.
- **Dependency Mapping**: The `Task.depends_on` attribute is currently initialized but not utilized by the `execute()` loop; this could be used to implement a Directed Acyclic Graph (DAG) for parallel task execution.
- **Custom Patterns**: New navigation intents can be added by appending new regex patterns to `_ROUTE_PATTERNS` or adding strings to the keyword tuples.
