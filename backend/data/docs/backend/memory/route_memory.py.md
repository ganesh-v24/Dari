# backend\memory\route_memory.py — JSON-backed cache for geocoded coordinates and computed routes

## Overview
This file implements a persistent caching layer designed to store the results of expensive geocoding and route computation operations. By mapping a unique hash of start and end locations to a payload, it prevents redundant API calls and reduces latency for frequently requested navigation paths.

## Architecture Role
- **Layer**: Persistence / Memory
- **Pattern**: Singleton / Cache-Aside
- **Dependency direction**: Receives calls from routing services (e.g., navigation logic); calls the local filesystem via `pathlib`.

## Key Concepts (Basics → Advanced)
1. **Deterministic Keying**: To ensure consistent lookups, the system uses `_key()`. It concatenates the start and end location names with a delimiter (`::`) and generates an MD5 hash. This ensures that the cache key remains a fixed length regardless of the input string size.
2. **JSON Persistence**: The cache is not merely in-memory; it is serialized to a JSON file at `ROUTE_MEMORY_PATH`. This allows the "memory" of the agent to persist across application restarts.
3. **Null Handling**: The system explicitly handles cases where the `start` location might be `None` (e.g., "current location") by substituting it with a `__NONE__` placeholder before hashing.
4. **Atomic-like Writes**: Every `set()`, `forget()`, and `clear()` operation triggers a full rewrite of the JSON file to ensure the disk state matches the in-memory state.

## Data Flow
1. **Request**: A service calls `get(start, end)`.
2. **Key Generation**: `_key()` transforms the location strings into an MD5 hash.
3. **Lookup**: The `_store` dictionary is checked for the hash.
4. **Return/Store**:
    - If found: The cached `dict` is returned immediately.
    - If not found: The service computes the route, then calls `set(start, end, payload)`.
5. **Persistence**: `_save()` converts the updated `_store` to JSON and writes it to `route_memory.json`.

## Gotchas & Extension Points
- **Performance Bottleneck**: The current implementation calls `_save()` (a full file write) on every single update. For high-frequency writes, this should be replaced with a write-back strategy or a proper database (e.g., SQLite).
- **Memory Growth**: There is no TTL (Time-to-Live) or LRU (Least Recently Used) eviction policy. The cache will grow indefinitely until `clear()` is called manually.
- **Extension Point**: To support more complex queries (e.g., different transport modes like "walking" vs "driving"), the `_key` method should be updated to include a `mode` parameter in the hash string.
